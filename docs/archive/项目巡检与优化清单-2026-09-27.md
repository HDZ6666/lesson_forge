## 3. 必须先解决的问题

### P0-01：大快照无法正式入库【生产阻断已复现】

证据：`service/plugins/bank/service/collector_client.py:27` 与 `question_apply_service.py:52` 均设置 `MAX_SNAPSHOT_ROWS = 100_000`；客户端在统计校验和分页汇总两处检查，业务服务标准化时再次检查。

使用生产计数调用只读校验函数，直接复现：`collector 快照 questionCatalogs 计数超过安全上限`。任务 18 的关系、标签、素材引用都超过该上限。详情页当前的轻量 eligibility 判断不能证明正式入库的全量校验会通过，应在产品上区分“快照完成”和“入库预检通过”。

处理：统一容量契约，对不同集合分别定义行数、累计字节和单页预算；预检展示确切原因。配合下面的流式后台入库改造，避免单纯扩大上限后把问题变成内存耗尽。

验收：以任务 18 等规模数据在隔离环境完成预检、入库、计数及关系一致性校验；重复执行不新增重复数据；失败不留下半套正式题库。生产发布前完成可恢复备份，再进行真实业务验收。

### P1-02：入库仍是一个很长的 HTTP 请求【代码确认】

证据：`pc/plugins/bank/api/bank.js:402` 的 apply 沿用 `pc/src/utils/request.js:28` 的 10 秒超时；后端 controller 直接等待 `QuestionApplyService.apply` 完成。客户端虽然分页拉取，最终仍把五类集合全部汇总进内存。`question_apply_service.py:2097`、`:2170` 按来源读取全部正式目录和题目，新增题目循环内 `flush`（`:2216`）。

影响：即便去掉 10 万行限制，长请求、内存峰值、事务持锁和大量 SQL 往返仍会出现；浏览器超时也无法可靠表达后端到底完成到哪一步。已有素材下载并发限制不能解决整个入库生命周期问题。

处理：提交返回持久化入库任务 ID；后台执行“预检 → 差异计算 → 素材准备 → 分批暂存 → 原子发布”。保留已有 scope 状态 token、快照封存和幂等语义，增加心跳、阶段进度、失败原因、重试边界和提交前取消。查询与写入限定到相关 scope/来源题目 ID，使用批量写入；素材队列也应限制待调度任务数量。

验收：断开网页、服务重启、重复点击、素材失败均有明确状态；提交成功前正式数据保持一致；接口及时返回，后台资源峰值在机器预算内。

### P1-03：结束任务时清空已保存日志【代码与生产证据一致】

证据：`sync_run_service.py:1961` 从远程状态读取 `logTail`，`:2139` 进入更新流程；完成分支调用 `_finish`（`:2374`）。而 `_finish` 在 `:2761` 无条件写入 `_tail_text(handle.log_lines)`。正常远程任务没有把远程日志同步填入这个本地缓冲，因此终态写入覆盖了此前持久化的日志。

处理：远程日志与本地控制事件明确合并，终态更新不得用空值覆盖已有日志；根据持久化 job ID 恢复任务 18 及可恢复历史任务。长期使用带序号的追加事件，状态表只保留摘要和有界 tail。

验收：完成、失败、取消、重启恢复后均保留此前日志；无新日志不清空历史；恢复操作幂等。当前任务 18 的日志仍可从 Collector 取回，并非全部丢失。

### P1-04：两阶段对比流程尚未完整实现【功能缺口】

证据：`question_review_service.py:14` 保存任务开始或首次查看时的目录基线，后续沿用该基线；`:125` 附近的题目接口返回采集预览和排除标记，没有读取正式题目进行内容差异比较。当前能看目录结构/数量变化和选择题目，但没有完整的“新增、修改、未变化”题目差异。

建议流程：

1. 比较当前正式目录与封存目录：新增、改名、父级变化、排序变化、本次未发现；同时展示采集是否完整。
2. 选择目录后比较题目：新增、题干/答案/解析变化、标签变化、目录关联变化、素材变化、未变化；能查看具体差异并保留选择。
3. 汇总本次操作和数量，显示素材与容量预检结果，确认后提交后台入库。
4. 入库结果可追溯到采集快照、正式库版本和本次审核选择。

差异结果必须绑定正式库状态 token、采集快照 hash、审核 revision；任一变化都提示重新比较。任务开始时的基线可保留用于追踪采集过程，但入库确认应针对当前正式库重新验证。“本次未发现”不能直接推断为应删除，尤其对于不完整采集。

验收：数量相同但题干不同仍识别为修改；一题属于多个目录时题目内容和目录关系分别处理；审核期间其他任务入库后旧审核结果不能直接提交。

### P1-05：题库图片请求地址和鉴权不匹配【代码及路径探测确认】

证据：`pc/plugins/bank/utils/html.js:86` 生成 `/bank/question/.../asset/...`；浏览、题目管理等页面直接用于图片。生产接口前缀为 `/prod-api`，当前请求返回前端 HTML。后端 `bank_controller.py:937` 附近素材接口有权限校验，直接给 `<img>` 加 API 前缀仍不会自动附带 Axios 的 Bearer token。

处理：复用教案侧已采用的鉴权下载 Blob 方式，统一素材加载组件、缓存和 URL 释放；接口失败显示可识别原因。`getQuestionAsset` 已存在，但上述页面没有使用。

验收：登录用户在题库浏览、题目管理、教案预览均显示公式与题图；无权限访问仍被拒绝；切换题目/卸载页面后释放 Blob URL。正式库当前没有素材，仍需真实入库后做完整图片验收。

### P1-06：历史教案随正式题库变化【代码确认】

证据：`lesson_do.py:76` 的生成条目只保存题目 ID 等抽题信息；`lesson_service.py:521` 的详情每次读取当前 `qb_question` 与素材。虽保存 `rule_snapshot_json`，详情仍查询当前规则与方案。

影响：同一来源题目更新后，旧教案的题干、答案、解析和图片可能改变；历史导出无法稳定复现。

处理：生成时保存题目内容/素材摘要及版本、规则和方案快照；素材引用保持可追溯并避免被后续清理破坏。换题和重新生成产生明确的修订记录。

验收：生成教案后修改正式题库、规则与素材，原教案展示及导出的业务内容保持不变；主动重新生成才使用新版本。

## 4. 稳定性、性能与运维

### P1-07：备份与恢复能力没有可验证的闭环【运维缺口】

在当前仓库、用户/root 定时任务和 systemd 定时器中未发现该项目的自动备份流程；服务器已有 SQL 文件较旧，不能证明当前业务受保护。本轮无法排除云平台快照或其他外部备份，不能断言“绝对没有备份”。

应统一备份 MySQL、Collector SQLite、素材和必要配置，记录关联版本与时间点，设置异机保存、保留周期和失败告警。SQLite 使用在线备份机制或受控停写快照，不能只随意复制主文件而忽略 WAL。必须在隔离环境演练恢复和数据关系校验，再把“备份成功”视为有效。

### P2-08：Collector 启动绑定重型迁移【代码确认；具体耗时归因待测】

`collector/src/api/job_manager/index.cjs:97` 构造时执行元数据/快照迁移；`collector/lib/run_snapshots.cjs:905` 每次启动调用迁移，没有包裹整个迁移的显式事务。迁移包含移除并重建不可变触发器、旧列规范化扫描等。去重已有索引短路，不能说所有去重每次都会重跑。

改为有版本号、单一执行者、可回滚的迁移步骤，把一次性修复移出正常启动；评估 SQLite 事务边界和并发进程。补充启动阶段耗时、迁移状态与 readiness。中途终止迁移不能留下缺失的封存保护。

### P2-09：抽题和 Word 导出缺少规模与内容验收【代码风险】

- `lesson_dao.py:68` 一次加载匹配题目、关系和素材统计；每次模拟/生成/换题都可能重复做大范围查询。对章节和整本教材分别压测，预计算题目特征，按正式库版本缓存候选，保留抽题覆盖与确定性，避免随意截断候选改变抽题结果。
- `lesson_controller.py:241` 的 Word 导出逐个读取素材记录，然后在异步请求中同步生成文档。应批量查询素材，把耗时渲染移到线程或后台任务，并限制并发。
- `word_export.py:73` 起的表格处理把单元格图片变成 `[图]`；图片插入失败也静默变成 `[图]`。补充带公式、SVG、几何图、图片表格、多题小问的真实样本，明确格式转换和失败提示。尚未进行真实题库的 Word 视觉验收。

### P2-10：教案编辑并发与访问范围需要完善【代码风险/产品边界待定】

`lesson_service.py:446` 换题先读后写，`lesson_dao.py:285` 更新仅按 item ID，没有 expected revision；文字保存也是覆盖。并发标签页可能覆盖修改或触发唯一约束错误。建议教案级 revision 和冲突响应，换题时锁定必要记录；用真正的并发集成测试验证。

当前接口有功能权限，但教案查询等主要按 ID，没有逐条创建者过滤。若产品定义为教师个人空间，需要用户/组织数据范围；若明确为共享教案库，应文档化共享与编辑权限。本项不等同于已复现越权漏洞。

### P2-11：资源限制、日志轮转和发布可追溯性不足【线上配置确认】

- 检查的业务容器没有显式 CPU/内存上限，Docker 使用 `json-file` 且未见容器级轮转选项。共享服务器上应按角色配置预算，并核实 daemon 级日志策略。
- 巡检时内存约 3.7 GiB、Swap 已使用约 1.7 GiB；短时 `vmstat` 后两次采样没有换入换出，不能据此断言当前发生内存抖动。磁盘约 57% 使用，尚非磁盘满故障。需要持续监控内存峰值、Swap 活动、磁盘/WAL/日志增长和任务耗时。
- 生产前后端和 Collector 来自不同日期的增量部署；旧测试 Collector 仍用 20260910 镜像。不能直接把测试容器结果当作当前生产镜像的验证。
- 建立同一源码版本的构建清单，记录前端校验和、服务/Collector 镜像摘要、迁移版本及回滚步骤。当前未提交工作区状态不适合作为长期发布依据。
- 健康检查补充数据库、Collector 可用性与关键只读接口，告警区分进程存活和业务可用。避免在高频健康检查中执行重型扫描。
