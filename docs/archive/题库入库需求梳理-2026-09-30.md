# 题库入库需求梳理：面向自己或少量教师备课

> 已于 2026-10-01 归档。以下为历史原文，文中的“当前”“唯一入口”“下一步”和完成状态只指当时，不用于指挥本轮实施。接手请读[文档入口](../README.md)；当前需求以[重构实施规格](../重构实施规格.md)为准，进度以[实施任务清单](../实施任务清单.md)为准。

日期：2026-09-30。性质：需求分析与推荐方案；不表示自动入库已经实现或开启，也不改变线上数据。

后续需求已明确：当前先实现自动采集与全部教材覆盖，一个任务一本教材，之后才推进教案。总体范围、调度和验收顺序以[自动题库采集需求与实施方案](自动题库采集需求与实施方案-2026-09-30.md)为准；本文保留入库简化原则。

## 1. 已确认的用途与核心目标

用户本次确认：主要供自己或少量教师备课使用。

结合根 README、原抽题设计、现有 bank/lesson/collector 代码，核心使用流程是：选择教材与知识点，配置题型、难度、数量，抽题，预览和换题，编辑教案文字，导出 Word。当前不生成新题、答案或解析。

据此归纳的需求：

- 同步后题目尽快可用于备课，不需要逐道审核几万道题。
- 题干、公式、图片可显示，教材和目录归属正确，重复同步不重复加题。
- 有异常时知道哪些失败、为什么失败，并能重试。
- 人工禁用、人工题目及已保存教案得到保护。
- 教师判断重点放在本节课实际使用的题目和导出的教案上。

“整个教材每次以同一版本瞬间切换”“每题必须审批”“对外保证每题经过学科审核”尚不是已确认需求。

## 2. 推荐默认流程

选择教材 → 抓取并持续保存断点 → 单本教材收尾 → 自动检查和归类 → 后台分批入库 → 汇总结果 → 生成教案后预览、换题、导出。

正常数据自动处理，人工处理异常或重要变更。目录和题目对比保留为可查看的说明及异常处理工具，不要求每次先看完双树、再逐题确认、再点击发布。

首次接入来源或修改解析器后，做一次目录、题型、图片和导出样本抽查；这属于上线验收，不是以后每次同步都要审批几万道题。

## 3. 自动处理与人工处理边界

| 情况 | 推荐规则 |
| --- | --- |
| 稳定来源的新题，目录归属、题干、必要素材检查通过 | 自动新增 |
| 同一来源 ID，内容与关系未变化 | 跳过重复写入，记录本次已发现 |
| 同来源正常内容更新，检查通过且无人工保护冲突 | 自动更新并留来源、任务与变化记录；显著的批量变化先暂停确认 |
| 新增普通目录、明确来源 ID 的名称修正 | 自动处理；目录移动、教材归属变化等影响既有抽题规则的操作单独检查 |
| 缺图片、空题干、解析失败的个别题目 | 自动重试；仍失败则隔离并记录，保留已有合格题目，不用坏数据覆盖 |
| 任务身份/教材范围不符、扫描大范围异常、题量骤变或疑似解析器回归 | 暂停受影响范围的自动入库，提供具体原因与差异，由人工处理 |
| 本次没有抓到旧题、旧目录或旧关系 | 默认保留；不依据缺席直接删除或禁用，不用不完整扫描清理旧数据 |
| 来源未采集答案/解析 | 明确标记未采集，保留正式库已有可信内容，不生成答案 |
| 人工创建的题目、人工禁用的来源题目 | 不覆盖、不自动重新启用；有冲突时保留人工决定 |

自动检查证明的是数据符合导入规则和可用性条件，不证明每道题的数学内容或来源答案绝对正确。教师仍检查实际用于授课的教案。异常阈值需要根据来源及历史数据确定，不采用未经实测的任意百分比。

## 4. 技术复杂度控制

保留现有三端边界：Collector 保存采集事实与原始素材；Service 负责正式数据与规则；PC 展示任务、异常和备课结果。Collector 不增加直接写正式 MySQL 的第二条通路。

第一阶段可以沿用现有正式表，新增持久化后台入库任务和批次进度：

1. 自动检查后，按稳定来源 ID 去重；为本次允许处理的题目保存固定范围和结果。
2. 分批写入，每批独立事务；一道题本次涉及的内容、目录关系、标签和素材引用必须一致提交。素材先准备并检查，再允许题目进入可抽取集合。
3. 进度与批次提交一致记录，或在重启时通过批次结果重建；重复批次执行保持幂等，不能靠内存进度避免重复。
4. 先串行执行同来源的正式写入，避免多本教材同时更新共享题目造成竞争。保护其他教材仍在使用的关联与素材。
5. 允许已提交的合格批次逐步可用。代价是同步期间教材包含不同批次的数据，不能承诺整本教材原子切换。一次生成需使用一致的数据库读取结果，并保存实际题目及规则快照。
6. 失败后保留已提交的合格批次并继续重试，明确显示部分完成；不声称整个任务已回滚。不能继续套用“当前完整快照已经应用”的状态语义。
7. 保留原始采集快照、入库结果和必要的变更前值用于排查与受控恢复。整本题库的一键原子回退不是这一简化方案的承诺。

如果以后明确要求“同步期间全部用户始终只能看到整本旧版本或整本新版本”，再建设完整题库版本和统一切换。分批提交与整本原子切换是不同的产品保证，不能两者混称已实现。

## 5. 页面应当简化到什么程度

- 主操作：选择教材并开始同步。
- 主状态：采集中、检查中、入库中、已完成、部分完成/待处理、失败。
- 结果：新增、更新、未变化、异常、待确认分别多少；异常可查看原因并重试。
- 常规用户进入题库浏览或教案生成即可使用；目录/题目差异放在详情中按需打开。
- 保留采集状态和入库状态两个内部事实，但不要让用户在“审核通过、应用、发布批次、恢复”之间猜测题目是否已可使用。

同步中心、独立同步题库和离线包发布已有不同路径。常用页面优先收敛到一条；已有接口和历史记录不应为了简化界面直接删除。

## 6. 自动入库前必须修正的现有行为

本节是代码复核发现，不代表已经修复。

- `bank_service.py` 的来源题目管理允许人工启停；但 `question_apply_service.py` 会把采集到的题目 `status` 写为 `0`，并根据关联目录重新启用。因此需要区分人工禁用与同步可用性，避免下一次自动同步撤销人工决定。
- 当前 apply 有目录缺席后的禁用及关系整理语义。改成保守增量入库时，不能只在采集结束后自动调用现有 apply；必须明确保留未覆盖范围与本次未发现的数据。
- 当前大数据首批 CLI 只支持空来源库，正常 apply 又是全量长事务；自动入口本身不会解决增量和批次恢复。
- 现有 `isCurrent`、快照 hash 与应用历史表示完整快照的应用，不能用于证明过滤异常题后的部分批次已完整入库。
- 当前题目、目录、标签和素材可能跨教材共享，必须保留稳定 ID 和各来源/范围的归属，不能按章节简单删除再插入。

## 7. 本轮调整后的实施优先级

| 优先级 | 范围 |
| --- | --- |
| 必须先做 | 保护人工启停与人工题目；保守增量更新规则；完整性检查与异常隔离；持久化后台分批入库及恢复；准确的部分完成状态 |
| 直接改善备课 | 图片错误反馈、抽题预览与换题、Word 内容验收、历史教案快照、异常重试 |
| 保留但简化 | 目录/题目差异、变更历史、少量异常的批量确认；不作为每次同步的强制多步流程 |
| 按明确需求再做 | 整本版本原子发布、完整版本图谱、逐题强制审批、采集中实时传输候选版本、整本一键原子回退 |
| 仍然必要 | 可恢复备份、基本磁盘/日志管理、鉴权、并发编辑保护；这些不因使用人数少而消失 |

验收以用户结果判断：一批正常题目无需人工逐道确认即可使用；断线/重启能恢复；重复同步不重复；坏题不进入抽题候选；人工禁用不被撤销；异常不会隐藏；旧教案内容不随同步变化。

## 8. 与此前方案的关系

此前讨论的“先完整审核、再构建版本、整本统一发布”适用于需要整本原子一致性与严格发布管理的场景。用户已明确当前是自己或少量教师备课，因此将其从默认必做方案调整为可选演进方向。

巡检报告中的实际缺陷仍然存在，但“没有完整版本发布/强制逐题审核”不应继续单独作为当前备课功能未完成的判据。本文件记录推荐边界，不把提议写成已实现功能。
