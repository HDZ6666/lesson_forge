## 1. 冻结决策

第一版题库的插件 ID 固定为 `bank`，是若依全栈插件：

```text
service/plugins/bank/   # FastAPI 后端、migration 和独立 Publisher
pc/plugins/bank/        # Vue 3 管理端插件
```

采集器继续是独立 Node/Playwright 工程：

```text
collector/legacy/zujuan_sync.cjs（2026-09-07 归档为旧入口）
```

采集器不作为 FastAPI 模块导入，不在浏览器进程中连接 MySQL，也不由管理端页面直接控制浏览器。它先把结果写入 SQLite；`collector/qbpkg.cjs` 把已关闭的 SQLite 规范化为不可变发布包；`plugins.bank.publisher` 再把发布包装载到 MySQL 影子表并切换。

第一版只支持 **MySQL 8 + InnoDB + 一个目标 schema**。PostgreSQL、多目标 schema、跨版本在线迁移和搜索引擎不在本计划内。

线上永久保留以下当前业务表，以及两个数据集元数据表：

```text
qb_textbook_version
qb_textbook
qb_catalog_node
qb_question
qb_question_catalog
qb_question_tag
qb_question_asset
qb_sync_batch
qb_dataset_meta
```

七张业务表只保存当前发布数据，不以 `batch_id` 长期保留多份业务快照。每次发布前创建七张影子业务表和一张 `qb_dataset_meta` 影子表；二次校验通过后，在同一条 `RENAME TABLE` 语句中原子切换。`qb_sync_batch` 是发布审计和状态表，不参加切换。被换下来的旧表只作短期热回退；发布包才是长期归档。

## 3. 发布包契约（`.qbpkg`）

### 3.1 包内文件

`.qbpkg` 是一个不可变目录或归档包，根目录必须包含以下五个文件；有本地素材时可以另外包含内容寻址的 `assets/` 成员：

```text
manifest.json
snapshot.sqlite3
diff-report.json
validation.json
checksums.sha256
```

工具以临时目录构建，所有文件关闭并自验证后再原子改名为最终包名。已存在的包不覆盖；同一 `batchNo` 不得对应不同内容。包生成后禁止修改 SQLite、JSON、文件名或校验和。

`checksums.sha256` 对除自身外的所有包成员逐个列出 SHA-256 和相对路径；它自身不把自己列入校验范围。读取包时拒绝缺文件、额外不安全成员、路径穿越、重复路径、大小异常和校验不匹配。

### 3.2 `manifest.json`

当前格式版本为 `1`，字段名以已实现工具为准：

| 字段 | 规则 |
| --- | --- |
| `formatVersion` / `schemaVersion` | 当前分别为字符串 `1` / `2` |
| `batchNo` | 非空批次号，对应 `qb_sync_batch.batch_no` |
| `createdAt` | UTC ISO 8601；可显式传入以支持可重复构建 |
| `sourceProvider` | 必填，并与 snapshot 所有行的 `provider` 一致 |
| `fullSnapshot` | 必须为 `true` |
| `dataset` | 显式提供的版本、教材和来源元数据，不能猜测 |
| `counts` | snapshot 七张表行数 |
| `snapshotSha256` | `snapshot.sqlite3` 的 SHA-256 |
| `rangeEvidence` | 非空同步范围及完成证明 |

题目全文只在 `snapshot.sqlite3` 中。manifest 不放凭据，不把运行时间或名称哈希冒充来源真实 ID。

### 3.3 `snapshot.sqlite3`

这是发布数据载荷，不是采集器运行数据库。当前实现包含与线上七张业务表同名的七张工具 snapshot 表，不包含运行锁、断点、临时错误和浏览器原始页表；`qb_dataset_meta` 是线上 MySQL 当前指针表，不是 snapshot 的第八张表。snapshot 使用 `provider + external_id` 候选身份；发布器映射为 MySQL 的 `source_provider + external_*_id` 并从当前正式表复用本地主键，不能直接把 SQLite 文件替换线上表。

导出器必须在包内完成以下确定性处理：

1. 补齐数据集、版本和教材的业务上下文；缺失且无法配置时阻止发布。
2. 保留 collector 外部键；核心实体缺失稳定外部 ID 时阻止自动发布，不生成假 ID。
3. 将题目 HTML 中允许的第三方 `img[src]` 规范化为 `data-asset-key`，并为每个引用建立素材行。
4. 目录成员关系生成 `query_catalog/query_membership`；页面知识点和筛选标签保留各自证据类型。
5. 只把采集到的组卷次数映射到 `assemble_count`；`reference_count` 未采集时必须为 `NULL`。
6. 生成 `diff-report.json` 和 `validation.json`；任何阻断级缺口都不能生成可批准包。

### 3.4 当前已实现的 qbpkg 命令与差异

当前可执行入口位于 `collector/qbpkg.cjs`，包装脚本为 `qbpkg:build` 和 `qbpkg:verify`。构建必须显式给出完整快照和范围完成证据；输出路径已存在时拒绝覆盖。manifest 字段即第 3.2 节契约。

当前 qbpkg snapshot 的真实字段边界来自 `collector/lib/qbpkg/schema.cjs`：外部键为 `provider/external_id`，题目仍有 `ease_coefficient`、`assemble_count`、`reference_count`、`year`、`region`、`exam_type`、`answer_html`、`solution_html`；目录关系使用 `relation_type/evidence_type/query_fingerprint`；标签使用 `dimension/tag_external_id/tag_value/relation_type/evidence_type`；素材键由工具生成。验证器已检查 SQLite 完整性、外键、七表行数、孤儿关系、`reference_count` 全为 `NULL`、HTML 中的 `data-asset-key` 闭合、素材键哈希和包内素材摘要。

当前工具 snapshot 与 MySQL 列名并不相同：题目仍有 `ease_coefficient`、单个 `region`、`solution_html`，关系仍引用外部 ID。发布器负责显式列映射、外部 ID 到本地主键映射以及不支持字段置 `NULL`；禁止按列顺序盲拷贝。素材键算法以工具实现为准：`asset_type + '-' + SHA256(source_url)` 前 16 位。

## 4. 端到端数据流

```text
公开页面
  -> collector/legacy/zujuan_sync.cjs（旧入口）
  -> collector SQLite + raw gzip + 可选素材文件
  -> 关闭 SQLite 后构建 .qbpkg
  -> 校验 manifest/checksums/snapshot/diff
  -> MySQL 影子表装载
  -> 影子表二次校验
  -> 同一条 RENAME TABLE 原子切换
  -> qb_dataset_meta 指向新包，qb_sync_batch 记为 published
```

线上查询只读当前正式表。采集器、导出器和发布器均不得直接 `INSERT`、`UPDATE` 或 `DELETE` 当前正式七表；发布器只能写批次元数据和本批次影子表。

## 5. MySQL 在线字段级契约

### 5.1 通用约束

- 所有表使用 `ENGINE=InnoDB`、`utf8mb4`；时间字段使用 migration 中的 `DATETIME`。第一版不使用 MySQL `ENUM`，关键状态由 `CHECK` 和插件共同校验。
- 逻辑外键必须经过装载校验，但不创建跨影子表的物理外键，以免表名切换和回退被外键依赖阻塞。
- 本地主键使用 `BIGINT`。发布器加载候选数据时按 `source_provider + external_*_id` 查找当前正式表并复用内部 ID；新数据才分配新 ID。核心实体缺少稳定外部 ID 时阻止自动发布。
- `source_provider` 必填且第一版只能是 `zujuan`；它不能由页面标题推断，必须来自包清单并在所有源数据行中一致。
- 不额外生成名称哈希身份。来源外部 ID 是跨发布身份，内容哈希只用于差异判断，不能替代来源身份。
- 所有 `NULL` 表示“没有可靠采到”，空字符串不能冒充未知值。`status` 使用若依 `sys_normal_disable`：`0` 正常，`1` 停用。
- 表中 `create_time/update_time` 是本地写入时间；来源时间另存来源字段，不能把“昨日”“7日内”伪造成绝对时间。

- 当前树只证明供应商目录节点，不提供可直接落库的版本/教材业务名称组合；版本和册次必须由可信配置或后续页面解析补齐。
- 当前 `questions` 没有稳定的题号、年级、学期、地区、学校、考试类型、分数和结构化引用试卷字段；对应线上列保持 `NULL`，不得从 `source_title` 猜测。
- 当前 `use_count` 的页面语义是“次组卷”，只能映射 `assemble_count`。它不是引用试卷数；`reference_count` 未采到时一律 `NULL`，不得复制或推导。
- 当前 `solution_html` 是可选的页面可见答案/解析区域拼接，无法可靠区分答案和解析；没有明确分段时不填 `answer_html` 或 `analysis_html`，按权限/采集开关设置 `answer_status`。
- 当前 `provider_updated_at` 是页面文本，可能是相对时间；无法准确解析时只写 `website_time_text`，`external_updated_at=NULL`。
- 当前素材表只有来源 URL、类型和可选下载元数据，没有 `asset_key`、尺寸和 HTML 引用位置；导出器负责稳定键、尺寸探测和 `data-asset-key` 重写，失败则阻止发布或将该素材标为下载失败并保留题干。
- 当前题目内容 HTML 是页面 HTML，不能直接进线上；发布前必须做白名单清洗，移除脚本、事件属性、站点按钮和未经允许的链接。

## 7. 同步、发布与幂等

### 7.1 采集阶段

采集器的现有幂等键为 `provider + external_id`。页面事务同时写题目、关系、标签、素材和断点；一页未完整处理时不推进断点，重放页面依靠 SQLite `ON CONFLICT` 去重。核心外部 ID 缺失时阻止自动发布并进入人工处理。

### 7.2 包阶段

`batch_no` 是注册幂等键。相同批次号和相同包摘要重复提交时复用既有批次；相同批次号但摘要不同时拒绝。导出器先写临时包，完成五个根成员及可选素材校验后再原子改名。

### 7.3 MySQL 阶段

1. 插入或复用 `qb_sync_batch`，构建时为 `building/validating`；先取得 MySQL 命名发布锁。
2. 创建以批次唯一后缀命名的七张业务影子表和 `qb_dataset_meta` 影子表，结构版本必须与正式表一致。
3. 从 `snapshot.sqlite3` 批量装载影子表。所有逻辑外键、唯一键、来源域名、枚举值、HTML 素材键和行数在影子表上检查。
4. 状态改为 `validated`，再进入 `approval_pending`；批准记录人、时间、包摘要和校验摘要。
5. 批准后状态为 `publishing`，执行一条 `RENAME TABLE`：将当前八表改成带旧批次后缀的旧表名，同时将八张影子表改成正式表名。八次改名必须在同一条语句中完成，`qb_sync_batch` 不在语句中。
6. 重新读取正式 `qb_dataset_meta`，确认包 ID、摘要和行数一致，再把批次置为 `published`。更新批次失败时由恢复器根据元数据事实补记状态，不重复装载。

发布器绝不通过 `TRUNCATE`、`DELETE` 后再填充正式表，也不在正式表上逐行覆盖。影子表不允许被查询接口当作当前数据暴露。

## 8. 状态机、批准、崩溃恢复和回退

### 8.1 批次状态

```text
building -> validating -> validated -> approval_pending -> approved -> publishing -> published
    |           |            |              |               |
    +-----------+------------+--------------+------------> failed
published/archived -> 新建 batch_type=rollback 的 publishing 批次 -> rolled_back
published -> archived
```

数据库 `CHECK` 固定允许：`building`、`validating`、`validated`、`approval_pending`、`approved`、`publishing`、`published`、`failed`、`archived`、`rolled_back`。同一包重试只能复用批次或创建明确的新批次，不能偷偷重置历史状态。

批准规则：`validated` 只能由校验器产生；`approved` 必须由具备发布权限的用户确认包摘要、行数、差异和警告；阻断级 validation 错误、摘要不一致、当前已有未完成发布或来源授权未确认时不可批准。只读查询权限不能批准、发布、回退或清理。

### 8.2 崩溃恢复

- 采集器崩溃：SQLite WAL、页事务和断点保证已提交页可重放；运行记录结束时标为失败/阻断，未完成页不标完成。
- 包构建崩溃：临时目录不视为包；启动恢复只清理带明确临时命名和校验失败的临时文件，不能删除已归档包。
- 影子装载崩溃：批次保持 `publishing` 或转为 `failed`；恢复器先检查影子表结构、包摘要和计数，合格则续装或重建，不触碰正式表。
- `RENAME TABLE` 前崩溃：正式表仍为旧版本；丢弃或继续校验影子表。
- `RENAME TABLE` 过程中不会出现半切换状态；MySQL 原子语句的结果只能是全旧或全新。重启后以正式 `qb_dataset_meta.current_batch_id/dataset_hash` 和表组命名核对事实。
- 切换后、批次状态更新前崩溃：恢复器发现元数据已指向包摘要时，只补记 `published`，不再次切换。
- 清理过程中崩溃：保留完整旧表组和批次记录，下次在同一发布锁内按严格条件继续，不删除单张孤立表。

### 8.3 热回退与清理

回退只能针对一整组同批次旧表，先取得发布锁并二次确认目标批次、包摘要和表组完整性；使用一条反向 `RENAME TABLE` 将当前八表与旧八表原子互换，再校验元数据。回退不删除发布包；它创建新的 `batch_type=rollback` 审计行并最终置为 `rolled_back`。

MySQL 不自动清表。发布器只有在以下条件全部满足时才可将旧表组置为可清理并执行删除：

1. 旧表组的八张表齐全，属于同一个已记录批次，且不等于当前 `current_batch_id` 或 `previous_batch_id`。
2. 新批次已完成二次校验并成功发布，至少有一份可读取且摘要匹配的长期 `.qbpkg` 归档。
3. 没有发布、回退、备份或人工检查进行中；保留期已到，且运维批准清理。
4. 最近备份/快照可验证，清理不会删除唯一可回退版本；清理前后记录表名、批次和摘要。
5. 清理命令按完整表组执行；发现缺表、名称不匹配、状态不一致或锁失败时整体停止。

旧表是短期热回退，发布包是长期归档；二者保留周期和删除权限必须分开配置。第一版不实现自动按时间清表。

实现页面、权限、回退和严格清理。验收：无权限用户无法操作；回退可原子恢复上一组表；发布包长期可读；清理条件不满足时不会删表；窄屏页面、HTML 清洗和素材失败占位通过验收。

## 11. 禁止事项

- 不把采集器搬进 FastAPI，也不让管理端绕过发布包直接写 MySQL。
- 不在正式七表上先清空再导入，不用逐行覆盖模拟发布，不用 `batch_id` 在业务表中长期复制每一版。
- 不把组卷次数当引用次数；不把缺失字段填成空字符串、假 ID 或推导值。
- 不把 `query_membership` 写成 `provider_asserted`；不丢弃关系证据或来源提供商。
- 不把原始第三方 HTML、任意本地路径或未校验 URL 直接暴露给前端。
- 不新增逐题同步错误/同步任务业务表；同步审计集中在 `qb_sync_batch`，系统调度仍使用现有底座能力。
- 不以一次“未看到题目”删除当前数据；差异中的删除必须经过发布策略、批准和完整包校验。
